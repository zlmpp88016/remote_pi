# 迭代需求（2026-11-09）

> 原始需求，按用户原话记录，未做改写。设计与拆分见后续 plan 文档。

## 背景

iOS 端已完成配对，但暴露出架构层面的问题。以下 6 条为本次迭代要解决的全部内容。

## 1. 不能灵活切换配对

这个需要可以灵活切换或者几个配对同时存在，就是一个客户端可以随时连接几个不同的 server。

## 2. 工作空间行显示"上次配对: xx ago"很多余

同一个配对空间，每个工作空间下都有一模一样的 "上次配对: xx ago" 这个很多余，要把这个替换成具体的 pwd 工作路径。

## 3. "8 个在线"没有意义

现在手机端连接当前这台机器的 server，发现有 8 个在线，这是什么意思？8 个 pi 吗？如果不是 8 个 pi，那这个在线就没有意义。

你要重构在线、离线的概念，最好是**全部、在线、离线都是针对 server 而言的，相当于 room**。一个 room 是在线，就相当于一个 room 的 server 已经建立连接了，而不是根据工作空间来，这个没有意义的。

## 4. 中继、默认中继概念混乱

为什么手机端还有什么中继、默认中继？现在都是切换成 server 直连了，app 里面的设置页面一个单独的中继放在哪是什么意思？我添加配对到另一台电脑的 server 上，那这个中继是第一台的 server 地址还是第二台的 server？

## 5. 布局全面调整

问题与 3 类似，应该是 **room → 工作空间 → 会话** 这种布局：

- 最外层是 rooms，对应一个个 server，有离线、在线状态。比如每隔十几秒发一个请求看看通不通，通了那就是在线。
- 点进去之后就是 server 管理的一个个工作空间，这个时候可以新建工作空间 —— 其实就是选择指定文件夹，在这个文件夹启动一个 pi 进程并记录。
- 然后点进去工作空间可以看到会话，切换会话就是 `/resume` 命令这种，新开会话就是 `/new`。
- 最好限制 server 在同一个工作空间下只能启动一个 pi 进程，否则可能会进程数量爆炸。

## 6. 本地数据库加速加载

探索一下 pi 是否有本地数据库用来管理会话的。

- 如果有，你可以利用这个数据库来加快工作空间或者工作空间下的会话的加载速度。
- 如果没有，则需要建立一下本地数据库 sqlite，安装 server 时需要单独装一个本地的 sqlite 给 server 专用。加载 pi 时存一些数据到数据库里面，以加快客户端获取工作空间、工作空间下的会话历史、会话中的历史记录等。
